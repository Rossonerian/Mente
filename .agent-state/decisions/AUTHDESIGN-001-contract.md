Frozen auth gateway contracts (to be implemented by AUTHSEC-001):

- POST /v1/auth/sign-in accepts email/password; successful response uses Supabase session shape access_token, refresh_token, expires_in, token_type, user. Frontend installs with provider setSession. Every rejected credential result is HTTP 401 with detail "Unable to sign in. Check your details and try again." Provider availability failure is HTTP 503. Server pads credential failures to common timing floor, uses shared database account/IP/device limits and audits hashes only.
- POST /v1/auth/sign-up accepts email/password/display_name. Always successful accepted signup response contains message "If this address can receive an account email, check your inbox for the next step." and requires_confirmation true; weak/breached passwords return safe HTTP 422 without account lookup details. Screening dependency outage fails closed HTTP 503.
- POST /v1/auth/recover and /v1/auth/resend accept email. Always HTTP 200 generic inbox message; shared rate limiting. Email confirmation/recovery uses provider OTP token entry (email + six digit code) to avoid implicit URL token leakage. Token input allows provider configured OTP length; profile/domain APIs remain admission gated.
- POST /v1/auth/admit-password accepts password with verified bearer provider session; successful provider reauthentication MUST match verified subject before screening/application admission. Used after recovery or MFA operations if session admission absent. Raw passwords never persisted or logged.
- POST /v1/auth/password accepts password with verified bearer; server checks strength/breach then provider password update. Successful response requires fresh sign-in, existing application sessions revoked globally. Recovery session may access this endpoint even when application admission absent, but must pass real provider session and current email confirmation checks.

Provider session existence/unrevoked refresh lineage checked, email confirmation mandatory; admission absence yields admitted false. Domain APIs require admitted true; verified enrolled MFA requires aal2. This status endpoint is available at aal1 to support challenge only, and never reveals domain data.
