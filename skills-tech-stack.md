# Service A — Skills & Technology Stack

**Service:** Memory Assistance Calling Companion  
**Scope:** Technologies and team skills required for the hackathon prototype  
**Constraint:** Service A shares one FastAPI backend and one Supabase project with Service B. Do not create a separate infrastructure stack. The implementation is an assistive prototype, not a diagnostic medical device or clinically validated assessment.

Service A has no patient frontend. Caregiver configuration is supplied by Service B, while Service A writes the canonical shared `CognitiveSession` and `SessionMetric` records with `source=CALL`. Its daily session contains 5–8 evaluated questions with day/time orientation first.

## 1. Preferred Stack at a Glance

| Area | Preferred default | Prototype use |
|---|---|---|
| Language | Python 3.12+ | Call orchestration, API, scheduler, answer rules, metrics, alerts |
| API framework | FastAPI + Uvicorn | Caregiver APIs and Twilio webhook/TwiML endpoints |
| Telephony | Twilio Programmable Voice | Real outbound calls and call lifecycle |
| Speech input | Twilio TwiML `<Gather input="speech">` | Speech transcription during the call |
| Speech output | Twilio TwiML `<Say>`; `<Play>` for family clips | Warm prompts and pre-recorded family voice recognition |
| Messaging | Twilio Messaging | Same-day caregiver SMS and optional routine summary |
| Scheduling | APScheduler | Daily calls and one bounded reschedule |
| ORM/migrations | SQLAlchemy 2 + Alembic | Shared relational model and repeatable schema changes |
| Database | Supabase Postgres | Shared CALL/GAME sessions, family data, alerts, and ML outputs |
| File storage | Supabase Storage | Private, consented family voice clips |
| Matching | Python normalization + RapidFuzz | Conservative matching against known answers/aliases |
| Validation/config | Pydantic + `pydantic-settings` | Typed payloads and environment configuration |
| Testing | pytest + HTTPX/FastAPI TestClient | Unit, webhook, repository, and mock-call tests |
| Quality | Ruff + mypy | Fast lint/format and useful type checks |
| Deployment | One Docker container on a public HTTPS host | Backend/scheduler reachable by Twilio |
| Local callback | Cloudflare Tunnel or ngrok | Temporary public HTTPS route during development |

No LLM, vector database, Kafka, Celery cluster, Kubernetes, or dedicated ML server is required.

## 2. Backend and API

| Technology | Used for | Why it fits the prototype | Skill required | Dependency / limitation |
|---|---|---|---|---|
| Python 3.12+ | All Service A business logic | Team-readable, strong telephony/ML ecosystem, same language as Service B ML | Intermediate Python; async basics; typing | Pin the exact minor version and dependencies in the lockfile |
| FastAPI | REST endpoints, Twilio webhooks, TwiML responses | Quick typed APIs, validation, autogenerated local API docs | Intermediate; routing, dependency injection, auth middleware | Webhook form parsing requires `python-multipart`; avoid long work inside request handlers |
| Uvicorn | ASGI server | Standard lightweight FastAPI runtime | Basic process/config knowledge | Run a single scheduler owner; multiple workers would duplicate jobs without coordination |
| Pydantic / `pydantic-settings` | Payload validation and secrets/config loading | Makes webhook/API boundaries explicit | Basic data modelling | Environment values must not be committed or logged |
| SQLAlchemy 2 | Database access and transactions | Mature relational mapping; supports standard Postgres | Intermediate ORM/query/transaction knowledge | Avoid both direct Supabase client writes and ORM writes to the same tables without a clear policy |
| Alembic | Schema migrations | Repeatable setup for judge/demo environments | Basic migration creation and upgrade/downgrade | Migration order must be tested on an empty database |

### Required backend skills

- Model the call as a finite-state machine rather than one long function.
- Return XML/TwiML quickly and move non-call-critical work after session finalization.
- Implement idempotency for provider retries using `CallSid`, step ID, and unique database constraints.
- Use transactions so a finalized session and its aggregate metrics cannot disagree.
- Keep logs structured but free of phone numbers, transcripts, names, and secrets.

## 3. Telephony, TTS/STT, and Messaging

| Technology | Used for | Why it fits | Skill required | Dependency / limitation |
|---|---|---|---|---|
| Twilio Python SDK | Create outbound calls and SMS | Official helper for Calls and Messages APIs | Basic API/SDK use; environment secrets | Trial accounts, country permissions, verified destinations, balance, and caller-number availability can block a demo |
| TwiML | Define each call turn | Deterministic call control without building media infrastructure | Intermediate XML/call-flow knowledge | Every `<Gather>` action must advance state; accidental reuse can loop |
| `<Gather input="speech">` | Capture spoken answers | Returns `SpeechResult` and may return `Confidence` | Speech prompt design; conservative result handling | Confidence is optional; provider/model/language support changes; line noise and accents affect accuracy; prompt-to-answer latency is approximate |
| `<Say>` with a tested neural voice | Speak prompts slowly and warmly | Minimal media preparation; provider-managed TTS | Language/voice testing; limited SSML | Voice and SSML support vary by provider and locale; do not promise untested NER languages |
| `<Play>` | Play uploaded family voice clips | Directly enables the voice-recognition question | Audio normalization and signed-URL handling | Twilio must fetch the file quickly; use supported audio encoding and short-lived URLs |
| Twilio status callbacks | Track initiated/ringing/answered/completed/failed/no-answer | Separates call transport state from cognitive results | Webhook lifecycle knowledge | Callbacks are asynchronous and may be repeated or out of order |
| `X-Twilio-Signature` validation | Verify webhook origin | Minimum credible protection for a public endpoint | Exact URL/proxy configuration | Signature validation fails if the externally visible URL is reconstructed incorrectly behind a proxy |
| Twilio Messaging | Same-day alert and optional routine-summary SMS | Reuses one provider and demonstrates caregiver notification | Basic messaging API and callback handling | SMS delivery is not guaranteed; the stored session summary or same-day `AlertEvent` remains authoritative |

Twilio documents speech/digit gathering and the optional transcript confidence in [`<Gather>`](https://www.twilio.com/docs/voice/twiml/gather), outbound Calls and status callbacks in the [Calls resource](https://www.twilio.com/docs/voice/api/call-resource), voice/language mapping in [Text-to-Speech](https://www.twilio.com/docs/voice/twiml/say/text-speech), and request validation in [Secure webhooks](https://www.twilio.com/docs/usage/webhooks/webhooks-security).

### Language implementation rule

The demo configuration contains an allowlist of tested `language_code + speech_model + TTS voice` combinations. English (India) or Hindi may be candidates, but the team must test the actual combination on a real call. Assamese and other NER languages are not enabled merely because a downstream provider lists them. If a required language cannot be verified, use a family-recorded prompt prototype or demonstrate in a verified language and state the limitation.

## 4. Scheduling and Background Work

| Technology | Used for | Why it fits | Skill required | Dependency / limitation |
|---|---|---|---|---|
| APScheduler | Daily call trigger, +60-minute reschedule, daily trend refresh | Runs inside the existing Python process; very little setup | Date/time handling; job stores; idempotency | In-process scheduling is not highly available; one runtime instance must own jobs |
| `zoneinfo` | Convert configured local time to UTC | Included in Python; supports IANA zones | DST/time-zone basics | Default may be `Asia/Kolkata`, but never store only a fixed offset |
| Database claim/idempotency key | Prevent duplicate calls | Safer than trusting an in-memory scheduler alone | SQL uniqueness/locking | Required even with one process because restarts/retries occur |

**Preferred demo behavior:** on startup, inspect schedules due in a small reconciliation window; create at most one missing attempt; never “catch up” by placing several calls.

**Alternative:** a managed cron endpoint. It is viable, but it adds a platform dependency and still needs idempotency. Use it only if the chosen host cannot keep APScheduler running during the demo.

## 5. Database and Storage

| Technology | Used for | Why it fits | Skill required | Dependency / limitation |
|---|---|---|---|---|
| Supabase Postgres | All relational data shared with Service B | Transactions, constraints, SQL analytics, and one unified source of truth | SQL schema/index/transaction knowledge | Cloud access is required; do not expose the service-role key to the browser |
| Supabase Storage | Family voice clips | Private buckets and time-limited access | Upload validation, MIME/audio handling | Signed media URLs must live long enough for Twilio to fetch but remain short-lived |
| Postgres unique constraints | Webhook/call/alert idempotency | Simpler and more reliable than in-memory duplicate checks | Data modelling | Define constraints before implementing handlers |

Supabase documents how Auth tokens and Row Level Security work together in [Auth](https://supabase.com/docs/guides/auth) and [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security). Service A normally accesses Postgres server-side; Service B browser access must still follow its own authorization policy.

### Minimum indexes

- `call_schedule(active, next_run_at)`
- unique `call_attempt(provider_call_sid)` when present
- unique `call_attempt(schedule_id, scheduled_local_date, attempt_number)`
- `cognitive_session(patient_id, started_at desc)`
- `session_metric(patient_id, recorded_at desc)`
- unique `alert_event(dedupe_key)`
- `family_memory(patient_id, type, active)`

## 6. Answer Evaluation and Metrics

| Technology / technique | Used for | Why it fits | Skill required | Limitation |
|---|---|---|---|---|
| Unicode/case/whitespace normalization | Prepare transcript and aliases | Deterministic and language-safe baseline | Basic text processing | Transliteration and code-switching still need explicit aliases |
| RapidFuzz | Conservative fuzzy match for known names | Small dependency; inspectable scores | Threshold calibration with fixtures | A fuzzy match must not override an ambiguous/low-confidence transcript |
| Python statistics/NumPy (shared) | Aggregate accuracy/latency and alert z-scores | Already needed by Service B ML | Basic numeric analysis | Small samples and near-zero variance need epsilon/minimum-history rules |
| Explicit rule tables | Gentle response and early-stop decisions | Easy to test and explain | Product/safety reasoning | Rules are observational, not clinically validated |

Do not add sentiment analysis, acoustic emotion detection, speaker recognition, or a generative grader. They increase risk without being necessary for the prototype.

## 8. Testing Stack and Required Competence

| Tool | Tests | Required knowledge |
|---|---|---|
| pytest | question planning, answer states, session scoring, safety thresholds, schedule rules | Fixtures, parametrization, deterministic random seeds |
| FastAPI TestClient / HTTPX | form-encoded Twilio webhook flows and REST contracts | ASGI client testing; headers; redirects |
| `respx` or a thin Twilio adapter fake | Twilio API success/failure without live cost | Dependency injection and mock boundaries |
| XML parser assertions | TwiML validity and correct action progression | Namespace/XML basics; do not compare brittle whitespace |
| Testcontainers Postgres or temporary Supabase branch | Constraints, idempotency, transactions | Integration-test setup; migration application |
| One physical-phone test script | Actual latency, STT/TTS, hang-up, no-answer, and reschedule | Follow a repeatable checklist and use consented/synthetic data |

### Minimum test fixtures

1. All-correct completed call.
2. Two incorrect answers followed by recovery.
3. Three consecutive incorrect answers and early termination.
4. Explicit “stop.”
5. Low-confidence/missing-confidence result classified `UNSCORABLE`.
6. “Not now” followed by one valid reschedule.
7. Busy/no-answer/provider failure without a cognitive alert.
8. Duplicate and out-of-order webhook callbacks.
9. Missing/expired family voice asset skipped without penalty.
10. Severe recognition fixture yielding one same-day alert and one SMS attempt.

## 9. Deployment and Configuration

### Preferred prototype deployment

- Build one Docker image for the FastAPI backend.
- Run exactly one scheduler-owning instance on a host with public HTTPS during the demo.
- Use a managed Supabase project shared with Service B.
- Configure Twilio callback URLs to that backend.
- Deploy Service B separately and allow its known origin.

### Required environment variables

| Variable group | Examples | Rule |
|---|---|---|
| Twilio | account SID, auth token, Voice number, Messaging number | Server only; never log |
| Database | Postgres DSN | Server only; use TLS |
| Supabase Storage | project URL, service-role key, bucket name | Service-role key is server only |
| Public URLs | backend public base URL, Service B origin | Exact external webhook URL matters for signatures |
| Scheduling | default time zone, reconciliation window | Pin conservative values for the demo |
| Feature flags | mock telephony, routine SMS, language allowlist | Mock adapter must be impossible to confuse with a successful live call |

## 11. Key Tradeoffs

| Choice | Preferred | Rejected/alternate | Reason |
|---|---|---|---|
| Backend | FastAPI modular monolith | Separate Node telephony service | One language for API and ML; fewer deployments |
| Scheduler | APScheduler | Celery + Redis | Celery adds infrastructure the demo does not need |
| Answer grading | Deterministic aliases + conservative fuzzy match | LLM grading | Known-answer flow needs predictability, not generation |
| Call audio | No recording | Record/transcribe full call | Raw audio is unnecessary and increases privacy/consent risk |
| Notification | Twilio SMS + stored alert | Push-notification service | Reuses existing provider; Service B already shows the durable alert |
| Deployment | One public container | Kubernetes/multi-region | Faster to build and sufficient for the judging window |

## 12. Future Production Considerations

If the concept advances, separately assess clinical study design, language co-design, consent/retention policy, health-data regulation, threat modelling, provider contracts, accessibility research, auditability, multi-provider failover, monitored scheduling, and incident response. None of these should delay the hackathon’s live call → shared data → caregiver signal path.
